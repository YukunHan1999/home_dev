# 1 环境管理

## 1.1 核心问题

随着玩的环境越来越多，日益增长的各种开发环境问题，日益增长各种技术栈，和 人类记忆力的局限性之间的矛盾上升为主要矛盾。利用工具进行管理复杂度，只需要花时间按规范写，读取时能够推断命名，快速重现曾经的研究。

## 1.2 降低复杂度的思维

软件工程思维：

### 1.2.1 模块化

```plaintext
本质：依赖（内部依赖，外部依赖）复杂度，依赖越多，关系越混乱，问题就变得无法处理。 
核心: 高内聚，低耦合
价值: 把复杂问题划分为可以处理的子问题，通过相互协作组成复杂系统
风险: 演化成本（升级与替换成本，沟通成本）
量化: 
	a. 业务问题是否已经到达过于复杂（不得不拆分）
		aa. 如何定义过于复杂?
			1. 发版或者解决一个bug,无意之间由于历史版本原因引入其他bug的事件 （Bug 频率 × 严重性）
			2. 日志输出文件膨胀巨大 （工具成熟度 vs 系统复杂度）
				2.1 即便引入了更好的日志聚合/分析工具（比如 ELK、Prometheus）和 良好的可观测性设计
， 				2.2 内部状态难以追踪，定位排查问题仍然需要花费大量时间
			3. 监控管理，维护，发版的面临成本 （人力 + 时间 + 业务损失）
				3.1 人力投入多
				3.2 时间消耗长
				3.3 业务损失大
				3.4 MTTR(平均恢复时间)
				3.5 部署频率
		ab. 当已经面临不得不拆分，即便模块拆分会带来新的数据一致性问题，也需要拆分。
			aba. 能否区分出是否是主业务逻辑，还是辅业务逻辑？
				abaa. 可以区分
					abaaa. MQ处理最终一致性问题处理？ 引入新的问题（SLA）多久一致性, 补偿机制（重试， 死信队列）
				abab. 不可区分
					ababa. 我会考虑 分布式锁，两阶段提交（2PC），基于事务消息处理 强一致性
	b. 交互频率低与交互强度（是否同步，是否有事务约束）
	c. 业务边界为主，技术边界为辅，二者协调
	d. 定义人类可接受范围的复杂度（小团队几个模块足够， 大团队可能需要处理几十个服务）
		da. 团队规模
		db. 工具链的熟练度
		dc. 认知负担

处理：
	横向切分：微服务（架构风格），DDD
	纵向切分: 分层（代码组织）
```

### 1.2.2 黑盒抽象

```plaintext
本质：关注与问题域相关特点，忽略其他与问题域无关特点
核心: 关注点分离，对于使用方的，是否好用
价值：使用方聚焦关注点，提供方实现的可替换
风险: 投入产出比，认知负担，可测试性
量化：使用方易理解，易用。

处理：
	接口: 统一行为
```

### 1.2.3 DSL

```plaintext
本质：代码也是数据，被加载，编译，运行，管理
核心：问题被定义的复杂度
价值: 表达力与限定性
风险: 被接受，学习曲线，维护成本
量化：写DSL与写库的边界在哪里？

数据驱动：创造解析引擎，用新的语言定义并处理特定领域问题。
```

## 1.3 核心工具

### 1.3.1 代码管理

Git Repo:

```plaintext
优点：
	1. 分布式，速度快，灵活分支
	2. 版本化， 差异性存储变更
	3. 多分支独立变更
缺点：
	1. 学习使用成本
	2. 协作与冲突
	3. 性能存储，大型项目性能下降，仓库膨胀，不适合大型二进制文件
	4. 技术限制 （）

处理:
	1. 建立规范（提交格式，分支策略， 冲突解决流程）

📌 Git 风险规避清单

1. 提交与版本管理
	避免误操作：谨慎使用 reset --hard、rebase 等破坏性命令，必要时加上 --no-ff 保留历史。
	提交信息规范：采用统一格式（如 Conventional Commits），避免模糊描述。
	小步提交：保持提交粒度合理，便于回滚和定位问题。

2. 分支策略
	明确分支模型：选择 Git Flow、Trunk-based Development 或简化版分支策略，避免分支混乱。
	保护主分支：对 main/master 开启保护，禁止直接 push，强制 PR 审核。
	定期合并：避免长期分支漂移，减少冲突风险。

3. 冲突与协作
	提前同步：开发前先 git pull，减少冲突。
	代码审查：通过 PR 审核发现潜在问题，避免错误进入主分支。
	自动化测试：CI/CD 在合并前自动跑测试，降低引入 bug 的风险。

4. 大型项目与性能
	避免仓库膨胀：不要提交大文件，使用 Git LFS 管理二进制文件。
	定期清理历史：使用 git gc 或 filter-repo 清理冗余历史。
	子模块/子仓库管理：合理使用 git submodule 或 git subtree，避免嵌套仓库混乱。

5. 安全与权限
	SSH 优先：使用 SSH key 而不是 HTTPS 密码，避免凭证泄露。
	最小权限原则：限制仓库写权限，避免误操作。
	签名提交：关键项目使用 GPG 签名，保证提交来源可信。
```

### 1.3.2 镜像管理

Docker:

```plaintext
优点：
	1. 隔离性，资源配额，镜像差异化存储。
缺点:
	1. 性能与资源损耗 （性能损耗，网络延迟，资源消耗）
	2. 安全性 （共享内核风险，容器逃逸， 权限管理复杂）
	3. 数据与状态管理 （持久化困难， 数据卷管理复杂）
	4. 学习成本（镜像优化，网络配置，存储卷， 安全策略， 编排工具）
	5. 大规模部署与运维 （管理复杂度（监控，日志，服务发现）， 编排工具依赖（kubernetes）， 多环境一致性）
处理：
	适合处理：微服务架构，CI/CD流水线，跨环境部署，快速测试场景
	不适合处理： 高性能计算（GPU/实时交易）， 超高IOPS数据库，对延迟及其敏感的应用。

1. 性能优化
	镜像优化：减少层数，使用轻量基础镜像（如 alpine）。
	资源限制：通过 --cpus、--memory 参数限制容器资源，避免资源争抢。
	网络优化：减少 NAT 层，使用 host 网络模式或优化 overlay 网络。
	缓存与构建：合理利用 Docker build cache，减少重复构建时间。
2. 安全加固
	最小权限原则：容器运行时避免使用 root 用户，使用 USER 指令。
	镜像安全：定期扫描镜像漏洞（Trivy、Clair），只用可信镜像源。
	内核加固：保持宿主机内核更新，启用 seccomp、AppArmor、SELinux。
	隔离策略：通过命名空间和 cgroups 控制容器隔离。
3. 数据持久化
	Volume 管理：使用 Docker Volume 或 Bind Mount 持久化数据。
	备份策略：定期备份卷数据，结合外部存储（NFS、Ceph、S3）。
	数据库容器化：谨慎对待数据库容器化，生产环境推荐独立数据库服务。
	日志管理：使用集中式日志系统（ELK、Fluentd）避免单容器日志膨胀。
4. 运维与监控
	编排工具：大规模部署时使用 Kubernetes 或 Docker Swarm。
	监控体系：Prometheus + Grafana 监控容器资源与服务健康。
	自动化 CI/CD：结合 GitLab CI、GitHub Actions，实现自动构建与部署。
	版本管理：明确镜像版本标签，避免使用 latest。
```
